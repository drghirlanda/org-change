* Note: New syntax in version 0.5

Starting with version 0.5, org-change uses a custom markup syntax instead of org-mode's link syntax. The old syntax ~[[change:old text][new text]]~ has been replaced by ~{!new text!}{!old text!}~. This change allows tracked changes to contain org links, LaTeX references, math, and any other org-mode or LaTeX syntax that was previously impossible to include. Comments can now be embedded as a third ~{!!}~ block.

If you have files using the old link syntax, you can convert them automatically by running ~M-x org-change-convert-from-links~ in each buffer. This converts all change links to the new format, including comments.

* Introduction

org-change is an Emacs minor mode that provides a simple "track changes" feature similar to some word processors. It works in any major mode, not just org-mode. The main use case is for authors to highlight changes between two versions of a document, such as before and after a round of review. For this, org-change provides:
- A custom markup syntax to mark additions, deletions, and replacements.
- Functions and key bindings to manipulate change markup.
- When used in org-mode, export filters for change markup (currently LaTeX, HTML, and plain text).

* Installation

Install from MELPA, or manually from here.

* Change markup syntax

org-change uses a two-group syntax where the first group contains the new text and the second group contains the old text:
#+begin_src org
  {!new text!}{!old text!}
#+end_src
Overlays hide the markup and old text, so you end up seeing only "new text." The hidden markup and old text are also made read-only, so an errant keystroke cannot delete a delimiter and break a change; you can still type freely just before, after, and inside the new text, and the change commands (accept, reject, comment, and the rest) edit the markup as usual. To indicate an addition, the old text group is empty:
#+begin_src org
  {!new text!}{!!}
#+end_src
To indicate a deletion, the new text group is empty:
#+begin_src org
  {!!}{!old text!}
#+end_src
In Emacs, deleted text is shown with a cross (✗) marker. If you cannot or don't want to use unicode, you can customize the marker as explained below.

You can add comments using an optional third group:
#+begin_src org
  {!new text!}{!old text!}{!A comment!}
#+end_src
In Emacs the comment is shown in italic just after the change. The easiest way to add or edit it is ~C-` c~ (see [[Commenting on a change]]).

Because the syntax uses ~{!~ and ~!}~ as delimiters, you can freely include org links, LaTeX math, citations, and any other syntax inside your changes:
#+begin_src org
  {!see [[https://example.com][this link]] and $E=mc^2$!}{!old text!}
#+end_src

** Escaping the delimiters

A change cannot contain org-change delimiters: the two-character sequences ~{!~ and ~!}~. To handle this, org-change escapes those sequences when it creates a change from a region, inserting a backslash to break the pair: ~{!~ becomes ~{\!~ and ~!}~ becomes ~!\}~. So marking the text =a!}b= as a deletion stores it as
#+begin_src org
  {!!}{!a!\}b!}
#+end_src
The escaping is undone automatically when you accept, reject, or export the change.

Two things to keep in mind:
- Escaping happens for text taken from a *region* (add, delete, replace, kill/yank). Text you *type by hand* into a change is inserted verbatim, so a hand-typed ~{!~ or ~!}~ is not escaped.
- In the annotated buffer you will see the backslash in the rare escaped change (=a!\}b=). It disappears when the change is accepted, rejected, or exported.

* Change manipulation

All org-change key sequences to manipulate change markup start with ~C-`~ (control + left quote). Not the prettiest, but few control prefixes are free. It's the curse of keymensionality. To change the prefix, see section [[Customization]]. Press ~C-` h~ at any time for a summary of the key bindings.

** Basic key sequences

- ~C-` a~ :: for additions.
- ~C-` d~ :: for deletions.
- ~C-` r~ :: for replacements.
All these act on the active region, marking it as added, deleted, or replaced text. In the case of replacement, the region is "deleted" (that is, tucked away in the hidden part of the change markup) and you can enter text in its place. You can also use ~C-` a~ without marking a region, and what you type next is marked as an addition.

** Moving between changes

To jump from change to change, use:
- ~C-` n~ :: move to the next change.
- ~C-` p~ :: move to the previous change.
Point lands at the beginning of the change. If point is inside a change, these move to the one after or before it.

** Overview of all changes

Press ~C-` o~ to open a side window listing every change in the buffer, one line each, prefixed with the line it is on. A change is summarized by the first line of its new text; a deletion, having none, is shown as its old text behind the deleted marker (=✗old text=). When ~org-change-show-deleted~ is on (see [[Showing deleted text]]), a replacement shows its removed text as well, as =new✗old=. The window is selected right away, so you can start moving through the list. In it:
- ~up~ / ~down~ :: move from change to change. The buffer being reviewed follows along, showing (and revealing, if folded) the change on the current line, so you preview each without leaving the list.
- ~RET~ :: jump into the buffer being reviewed, at the change on this line.
- ~e~ :: edit the change on this line. Focus moves to it in the source window, with point in its new text, so you can type. Accepting or rejecting it there (with the usual keys) returns you to the list; ~C-` g~ instead aborts, restoring the change to how it was when you started, and returns you to the list.
- ~a~ :: filter the list to one author, to the unattributed changes, or back to all.
- ~k~ / ~x~ :: accept or reject the change on this line. It acts on the buffer being reviewed and moves point to the next change. There is nothing to type in the list, so the accept and reject keys work without their ~C-`~ prefix; the full sequences work too, and both follow the keys you have customized.
- ~g~ :: refresh the list, if you have edited the buffer since opening it.
- ~q~ :: close the window.
Accepting or rejecting from the list refreshes it and leaves the cursor where it is, so the next change moves up into place: you can work down a document without moving at all. The list also keeps up with the buffer itself: accepting or rejecting there, whether one change or a whole region, refreshes it, so it never shows a change that is gone. It does not follow other edits, so press ~g~ after adding changes. The width and the side of the frame the window opens on are ~org-change-overview-width~ and ~org-change-overview-side~.

** Counting changes

Press ~C-` i~ to show, in the minibuffer, how many additions, deletions, and replacements the document contains, for example "3 additions, 2 deletions, 1 replacement".

** Commenting on a change

Press ~C-` c~ on a change to add or edit its comment. You are prompted for the text, pre-filled with the existing comment if there is one; entering an empty comment removes it. The comment is stored in the change's third group and shown in italic just after the change. If the change has an author (see [[Authors]]), it is shown as =author: comment= (for example =SG: needs a citation=), so you can tell who commented without having to remember which color is whose. A change that has an author but no comment shows just the author id.

In org-mode, if the target change is hidden inside a folded heading, the jump reveals it so you can see the change rather than just landing on the folded headline. Each jump first restores the fold state from the previous jump, so only the change you are looking at is expanded: stepping onward re-folds it and reveals the next one, leaving the rest of the outline as you had it.

** Moving text

To move sections of text from one place to another, you can use the key sequences ~C-` w~ for killing (Emacspeak for "cutting") and ~C-` y~ for yanking (Emacspeak for "pasting"). These work like ~C-w~ and ~C-y~ but mark the killed text as a deletion and the yanked text as an addition.

With no region active, ~C-` w~ acts on the change under point, so you can move something you have already added or replaced without having to select it around its invisible markers. Its new text is put on the kill ring and removed here: an addition is taken away entirely, while a replacement is left as a deletion of its old text (which stays deleted where it is). A ~C-` y~ at the destination re-adds the text there. If point is not on a change, or the change is a plain deletion with no new text to move, ~C-` w~ says so in the echo area and changes nothing.

** Accepting and rejecting changes

Key sequences are also provided to accept or reject changes:
- ~C-` k~ :: to accept the change under the cursor, or every change in the active region.
- ~C-` x~ :: to reject the change under the cursor, or every change in the active region.
- ~C-` K~ :: to accept as ~C-` k~ does, then move to the next change.
- ~C-` X~ :: to reject as ~C-` x~ does, then move to the next change.
- ~C-` b~ :: to go through all changes, starting at the current point, and accept, reject, or skip them. The ~b~ is mnemonic for "buffer" as you are processing all changes in the buffer.
"Accept" means to delete the change markup (including any comments) and insert the new text (or nothing, if the change is a deletion). "Reject" means to delete the change markup and insert the old text (or nothing, if the change is an addition). Point stays put: if it was inside the change, it is left on the same spot of the text that replaces it, so accepting or rejecting while you write does not send the cursor to the end of the paragraph. Where the two sides of a change come together, the gap between them is closed: deleting a word without its surrounding spaces does not leave a double space, and deleting a line or a paragraph without its newlines does not leave an empty line. When the two sides carry gaps of different width the wider one is kept, so a paragraph break survives next to a plain line break. Gaps are only closed when the change itself brought them together, so indentation, and blank lines or space runs written inside a change, are left as they are. The uppercase variants ~C-` K~ and ~C-` X~ do the same and then jump to the next change, so a document can be reviewed by holding one key; when there is no change left they say "No next change".

When the region is active, accept and reject work on every change that lies entirely within it, plus the change under the cursor, which is always taken whole even if the region only reaches into it. Other changes, including ones the region merely clips, are left alone. Emacs reports how many changes were processed, and the region is deactivated afterwards. Without an active region, the commands act on the change under the cursor, and say "No change at point" if there is none. You can accept or reject all changes in a document by selecting the whole buffer, but note that this deletes all changes. If you just want to export a clean manuscript, see section [[Producing a clean document]].

* Generating changes from two versions

If you already have two versions of a document -- say your draft and a revised copy from a coauthor -- you do not have to mark every change by hand. The command ~M-x org-change-from-diff~ takes the version in your buffer as the base, compares it against another version, and rewrites the buffer so the differences appear as tracked changes: text the other version adds is an addition, text it drops is a deletion, and reworded spans are replacements. Shared text is left untouched.

Because the changes are shown *over* your buffer, accepting them adopts the other version's text and rejecting them keeps what you had. In particular, rejecting all changes restores the buffer to its state before you ran the command.

The other version can come from either a file or git:
- By default, ~org-change-from-diff~ prompts for a *file* holding the other version.
- With a prefix argument (~C-u M-x org-change-from-diff~), it prompts for a *git revision* instead (default ~HEAD~) and uses the current buffer's own file as it was at that revision. If git is unavailable, the buffer is not under version control, or the revision cannot be read, the command reports the problem and leaves the buffer untouched, so you can fall back to the file version. Note that with git, accepting a change adopts the revision's text, so comparing against an older commit and accepting means reverting to it.

The comparison is word-based, so changes align on words and read naturally rather than character by character. If your buffer holds =The quick brown fox jumps.= and the other version is =The quick red fox leaps high.=, the buffer becomes
#+begin_src org
  The quick {!red!}{!brown!} fox {!leaps high!}{!jumps!}.
#+end_src
where ~red~ and ~leaps high~ are the incoming text and ~brown~ and ~jumps~ are yours.

The buffer is replaced in a single step, so ~undo~ restores it too. A couple of things to keep in mind:
- The comparison cost grows with the product of the two versions' sizes, so it is meant for documents and sections rather than very large files. If it is slow, run it on a narrowed region.
- Word alignment means a change may include the surrounding spaces (for instance ={!red !}{!brown !}=); this is cosmetic and accepts and rejects correctly.

* Authors

When several people review a document, org-change can attribute each change to its author and show it in the author's color.

Set ~org-change-author~ to your short identifier, for example "SG". Every change you then create is tagged with it, stored as an =@=-token in the change's comment:
#+begin_src org
  {!new text!}{!old text!}{!@SG!}
#+end_src
A change can carry both an author and a comment:
#+begin_src org
  {!new text!}{!old text!}{!@SG needs a citation!}
#+end_src

Register authors and their colors in ~org-change-authors~:
#+begin_src elisp
  (setq org-change-authors
        '(("SG" :name "Stefano" :color "royal blue")
          ("AB" :name "Alex"    :color "dark green")))
#+end_src
Each change is then tinted with its author's color in the buffer. On export the author becomes the ~changes~ package author: LaTeX writes ~\added[id=SG]{...}~ and injects a ~\definechangesauthor~ line for each registered author, while HTML adds an ~org-change-author-SG~ class to the change's spans. For LaTeX, use color names the ~xcolor~ package knows, such as "blue", "red", or "green".

If ~org-change-author~ is nil (the default), changes carry no author and behave exactly as before.

You can set the current author interactively with ~M-x org-change-set-author~, which completes over ~org-change-authors~ and offers a "No author" choice; an id you type that is not in the list is used as-is, with no color until you register it.

When several people have marked changes, you can review one at a time. In the overview (see [[A bird's eye view of the changes]]) each change shows its author, and ~a~ filters the list to a chosen author, to the changes that carry no author, or back to all. To dispose of a whole author's changes at once, ~M-x org-change-accept-by-author~ and ~M-x org-change-reject-by-author~ prompt for an author, count the matching changes in the region (or the whole buffer), and ask for confirmation before acting.

* Showing deleted text

By default, org-change hides replaced text and shows deleted text with a cross. You can choose to show this text by setting ~org-change-show-deleted~ to a non-nil value. The text will then be shown in the customizable face ~org-change-deleted-face~ after the change markup, and will be read-only. This is similar to some word processors, where deleted text is shown as strike-through (but you don't have to use strike-through).

To turn this on and off as you work, call ~M-x org-change-toggle-deleted-text~; it flips ~org-change-show-deleted~ and re-displays the buffer. If a change overview (see [[A bird's eye view of the changes]]) is open, it is refreshed too, so a replacement there gains or loses its removed text (shown as =new✗old=) to match.

Spaces in the shown deleted text are easy to miss, so each is displayed as a dash (=-=). This affects the display only; the buffer text is unchanged. Customize ~org-change-deleted-space~ to use a different string (set it to =" "= to keep spaces as spaces).

* Re-fontifying

If you change faces (see section [[Customization]]), you can apply the new settings by calling ~org-change-fontify~, which by default is bound to ~C-` f~.

* Exporting

Export is available when org-change is used in org-mode buffers. The export hooks are registered automatically when org's export framework loads.

** LaTeX export

When exporting to LaTeX, org-change uses the ~changes~ package, which it includes automatically in the exported document. org-change will then use the commands ~\added~, ~\deleted~, and ~\replaced~ provided by this package.

org-change supports comments via the third group, so that
#+begin_src org
  {!new text!}{!old text!}{!A comment!}
#+end_src
is exported to
#+begin_src latex
  \replaced[comment=A comment]{new text}{old text}
#+end_src
You can also sneak in other fields supported by ~changes~ at the end of the comment. For example, you can indicate the author of the comment:
#+begin_src org
  {!new text!}{!old text!}{!My comment,author=SG!}
#+end_src
which is exported to:
#+begin_src latex
  \replaced[comment=My comment,author=SG]{new text}{old text}
#+end_src
Lastly, you can set options for the ~changes~ package by setting the variable ~org-change-latex-options~. For example, you can place this code somewhere in your document and evaluate it:
#+begin_src org
  ,#+begin_src elisp
    (setq org-change-latex-options "[markup=underline]")
  ,#+end_src
#+end_src
Note that you need to include the brackets. The ~changes~ package also has configurations that are not set through package options, which you can set through ~#+latex_header:~ lines.

Note that the content of change markup is exported as raw LaTeX. This means org-mode markup like ~*bold*~ inside changes will not be converted. Use LaTeX commands directly instead (e.g., ~\textbf{bold}~).

** HTML export

When exporting to HTML, org-change produces ~<span>~ elements with classes ~org-change-added~, ~org-change-deleted~, and ~org-change-comment~. A replacement has both an added and a deleted span, while additions and deletions only have one span. The comment span is embedded in the added span when present, otherwise in the deleted span. So this:
#+begin_src org
  {!new text!}{!old text!}{!comment!}
#+end_src
becomes this:
#+begin_example
<span class="org-change-added">
  new text
  <span class="org-change-comment">
    comment
  </span>
</span>
<span class="org-change-deleted">
  old text
</span>
#+end_example
You can then use CSS to display these classes as desired.

** Plain text export

Exporting to plain text (the ~ascii~ backend, and the UTF-8 and Latin-1 variants of it) marks changes up as [[https://fletcher.github.io/MultiMarkdown-6/CRITIC.html][CriticMarkup]], the usual convention for tracked changes in plain text:
| change      | org-change                 | plain text          |
|-------------+----------------------------+---------------------|
| addition    | ={!new!}{!!}=              | ={++new++}=         |
| deletion    | ={!!}{!old!}=              | ={--old--}=         |
| replacement | ={!new!}{!old!}=           | ={~~old~>new~~}=    |
| comment     | ={!new!}{!old!}{!a note!}= | ={>>a note<<}=      |
A comment follows the change it belongs to, and an ~@ID~ author prefix is shown before it as ~{>>SG: a note<<}~, the way Emacs shows it on screen.

** Producing a clean document

When exporting, org-change looks first at the variable ~org-change-final~. This is initially ~nil~, meaning that the export proceeds according to the selected backend as detailed above. If ~org-change-final~ is not ~nil~, then only the new text is exported, resulting in a "clean" document without change markup. To achieve this, you can evaluate this code block before exporting:
#+begin_src org
  ,#+begin_src elisp :exports none :results silent
    (setq org-change-final t)
  ,#+end_src
#+end_src
This code can be anywhere in your file, even a ~:noexport:~ section.

* Customization

The key sequences, the deleted/replaced text marker, and the faces used to display changes can be changed through the customize interface:
#+begin_src org
  M-x customize-group RET org-change
#+end_src

* Adding exporters

To add an export format, add something like this to your org file:
#+begin_src org
  ,#+begin_src elisp
    (org-change-add-export-backend 'backend 'backend-function)
  ,#+end_src
#+end_src
where ~backend~ is a backend known to org-mode and ~backend-function~ is a function that produces the desired string from three string arguments: ~old-text~, ~new-text~, and ~comment~. The function can figure out whether the change is an addition, deletion, or replacement by looking at these variables: for additions, ~old-text~ is empty; for deletions, ~new-text~ is empty; other cases are replacements. The function should wrap its output in the appropriate ~@@backend:...@@~ export snippet so that org passes it through verbatim.

* Bugs and limitations

Please submit bugs and feature requests as [[https://github.com/drghirlanda/org-change/issues][issues on Github]].

- The content of change markup is exported as raw LaTeX (or raw HTML), bypassing org-mode's markup processing. Use the target format's commands directly inside changes.

- LaTeX export is not fully compatible with HTML export if you use the extended comment syntax. That is, HTML export does not handle extra arguments like "author=SG," which are a feature of the ~changes~ package for LaTeX.

- The delimiter escaping described under [[Escaping the delimiters]] applies to text taken from a region, not to text typed by hand into a change. A hand-typed ~{!~ or ~!}~ is left verbatim and can confuse the parser. Escaping also assumes your content does not already contain the exact escaped forms ~{\!~ or ~!\}~; on the rare occasion it does, they will be turned back into ~{!~ and ~!}~ when the change is materialized.
